# 세이브·설정 파일 봉인 (save seal)

English summary: an HMAC-SHA256 tag you append to a save or settings file so the game can notice casual edits and corruption. The key must live in the client, so it does not stop a determined attacker and proves nothing about who wrote the file; leaderboards and online rewards need server-authoritative state.

## 무엇을 하고 무엇을 못 하는가

`include/reshield/save_seal.h`의 함수 3개(`reshield_hmac_sha256`, `reshield_save_tag`, `reshield_save_verify`)가 전부다. 파일 I/O는 하지 않는다. 데이터 뒤에 32바이트 태그를 붙여 저장하고, 읽을 때 다시 계산해 비교한다.

| 막는 것 | 못 막는 것 |
|---|---|
| 메모장·헥스 에디터로 세이브·설정 값을 고치는 캐주얼 편집 | 키를 꺼낸 사람. 키는 클라이언트(바이너리, 프로세스 메모리)에 있으므로 문자열 검색이나 메모리 덤프로 찾을 수 있고, 찾으면 유효한 태그를 직접 만든다 |
| 잘린 쓰기, 동기화 중단, 디스크 손상 | 파일을 누가 썼는지 증명하는 것(진본성). 이 태그는 "키를 아는 프로그램이 썼다"는 뜻일 뿐이다 |
| 다른 키(다른 빌드, 다른 계정 값)로 봉인된 파일 | 옛 세이브로 되돌리기(rollback). 예전에 유효했던 파일은 지금도 유효하다. 카운터를 넣어도 카운터 값 자체가 같은 파일 안에 있다 |

전문 공격자(리버싱 도구, 메모리 편집기, 검사 분기 패치)는 막지 못한다. 막는다고 홍보하거나 그렇게 믿고 설계하면 안 된다. 이 기능의 목적은 싱글 플레이 세이브를 고치는 가장 흔한 캐주얼 치트에 마찰을 주고, 손상을 알아채는 것이다.

## 사용법

```c
#include "reshield/save_seal.h"
/* 저장: 데이터를 쓰고, 이어서 태그 32바이트를 쓴다 */
uint8_t tag[RESHIELD_SAVE_TAG_SIZE];
reshield_save_tag(KEY, sizeof KEY, buf, len, tag);
/* 읽기: 파일 끝 32바이트를 태그로, 나머지를 데이터로 나눠 검증한다 */
int ok = reshield_save_verify(KEY, sizeof KEY, buf, len, tag); /* 1 정상, 0 편집/손상, -1 인자 오류 */
```

- `-1`은 "검사하지 못함"이다(NULL, 키 길이 0 등). 편집으로 취급하지 않는다.
- 태그는 `HMAC-SHA256(key, "reshield-save-v1\0" || data)`다. 접두사는 같은 키로 만든 다른 HMAC과 섞이지 않게 한다. 순수 HMAC이 필요하면 `reshield_hmac_sha256`을 쓴다(RFC 4231 벡터로 테스트).
- 빈 키(`key_len == 0`)는 거부한다. 거의 항상 버그이기 때문이다.
- 비교는 상수 시간이다. 키 사본 같은 스택 임시값은 쓰고 나서 지운다(최선의 노력이며, SHA-256 내부 스크래치나 레지스터까지 완벽히 지운다는 보장은 아니다).

## 편집이 감지되면

세이브를 지우거나 게임을 종료하지 않는다. 캐주얼 편집을 한 사람은 대개 정상 구매자이고, 손상·동기화 문제로도 같은 결과가 나온다. 권장은 세이브에 `edited` 표식만 남기고, 온라인 보상·랭킹 같은 게임 규칙에서 제외하는 것이다. 로컬 신호는 위조 가능하므로 단독 근거로 제재하지 않는다.

## 키를 어떻게 정할까

키가 클라이언트에 있다는 사실은 바꿀 수 없다. 아래는 "얼마나 번거롭게 만드느냐"의 차이일 뿐이다.

1. **빌드마다 난수 키를 컴파일 타임에 넣기.** 빌드 스크립트가 32바이트 난수를 만들어 생성 헤더(`.gitignore` 처리)로 넣는다. 소스 저장소에 키가 남지 않고, 다른 빌드의 키와 다르다. 한계: 키는 바이너리 `.rodata`에 그대로 들어 있다. 문자열 난독화나 XOR 분할을 해도 실행 중에 조립된 키가 메모리에 나타나므로 "찾기 귀찮게" 하는 정도다. 더 큰 문제는 **빌드마다 키가 다르면 게임 업데이트 때 기존 세이브가 전부 검증에 실패한다**는 점이다. 그래서 키는 "세이브 포맷 버전"마다 두고(예: 포맷 v1·v2 키), 로드할 때 옛 키로도 검증해 본 뒤 새 키로 다시 봉인해 저장하는 편이 안전하다.
2. **사용자 값을 섞기(예: Steam ID).** `key = SHA-256(빌드키 || steamid)`처럼 계정마다 다른 키를 만들면 다른 계정에서 복사해 온 세이브가 통과하지 않는다. 한계: Steam ID는 프로필 주소로 누구나 알 수 있는 값이라 비밀이 아니다. 빌드키를 꺼낸 사람은 같은 식으로 계산한다. 즉 이것은 비밀이 아니라 **계정 묶기**다. 부작용도 있다: 계정을 바꾼 사람, Steam 오프라인 상태에서 ID를 얻지 못하는 경우, 가족 공유 계정에서 세이브가 열리지 않는다. 실패했을 때의 동작(편집이 아닌 "다른 계정" 안내 등)을 정해 둬야 한다.
3. **런타임에 서버에서 키를 받기.** 키가 바이너리에 없지만, 클라이언트가 받은 키는 결국 메모리에 있다. 오프라인 싱글 플레이가 깨진다. 이 정도 수고를 한다면 아래 서버 권위로 가는 편이 낫다.

## 멀티플레이·리더보드·온라인 보상은 서버 권위가 정답

클라이언트가 가진 세이브와 점수는 서버가 믿을 수 없다. 서버가 상태를 갖고(또는 서버가 서명한 값을 쓰고), 클라이언트는 입력과 요청만 보내야 한다. 이 태그는 오프라인 싱글 플레이 세이브의 손상 감지용이며, 온라인 기능의 신뢰 근거로 쓰면 안 된다. 같은 이유로 Steam Cloud는 세이브 내용을 검증하지 않으므로 태그가 맞아도 "클라우드에서 온 값이 정상"이라는 뜻은 아니다.

## 테스트와 호환성

`tests/test_save_seal.c`: RFC 4231 케이스 1·2·3·4·6·7(긴 키 포함), 키 64·65바이트 경계, 길이 0, 왕복, 모든 단일 비트 변조, 잘못된 키, NULL·길이 오버플로 인자. `make test`에 포함되고 Windows CI(`windows-msvc`)에서도 빌드·실행한다. 의존성은 없다(기존 `src/sha256.c` 재사용). 구조는 `<데이터><32바이트 태그>`이지만 이 라이브러리는 파일을 읽고 쓰는 함수를 제공하지 않는다. 포맷과 I/O는 게임이 정한다.
